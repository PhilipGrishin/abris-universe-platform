## 2. Overall Assessment

This is a high-quality pre-code design. Conformance with the approved product constraints is real, not declarative: the canonical Pattern is genuinely format-independent (ADR-TS001-001 §Decision; TD §5); Symbol≠PaletteItem and Pattern≠Progress are enforced by explicit invariants 3–4 and 8 (TD §5.3) with no uniqueness coupling; OXS `@marked` is mapped to nothing and warned (`OXS_SOURCE_PROGRESS_IGNORED`); unsupported content is counted, named, and preserved through retained source bytes with `completed_with_warnings` — no silent loss; `threadBrand: null` correctly refuses to invent DMC; tiled rendering is real from the first slice behind a `PatternRenderer` seam that preserves the future WebGL/500k migration path; dependency direction is strictly one-way into `domain-core`; save-success-equals-committed-transaction is the declared durability boundary; the deployment design uses immutable versions, least-privilege secrets, smoke-then-promote, no DNS mutation, and an honest TD-GATE-003 rollback anchor. ## 3. Required Rework (mandatory; blocking as stated)

**R-1 [High, pre-code — blocks domain-core/persistence] `deviceId` is missing from `ProgressEvent`.** TD §5.2 defines `ProgressEvent` without `deviceId`, but Task Package v1.1 §18 requires it explicitly (id, projectId, type, targetRef, timestamp, **deviceId**) and §21 mandates that the structure need no breaking migration for EP-15 sync ("idempotent id, timestamp, deviceId — уже в модели раздела 18"). Events are append-only and immutable from day one — the field cannot be backfilled later without the exact breaking migration §21 prohibits. Violated source: TASK-THINSLICE-001 v1.1 §18/§21. Closure evidence: `deviceId` (stable locally generated installation identifier) restored in the revised design and serialization tests; alternatively a formal Conflict/Deviation Report to the Project Owner — silent omission is not acceptable. Note: the design's replacement of `targetRef` (coordinate) with `targetStitchId` is **accepted** as a conscious refinement (deterministic stitch IDs resolve to coordinates); record it as such in the revision.

**R-2 [High, pre-code — blocks TD-GATE-001 acceptance and importer] The TD-GATE-001 fixture specification cannot detect axis errors.** TD §3/§6.3 requires "stitches at all four corners", a symmetric configuration: on a square grid with undifferentiated corners it cannot distinguish Y-mirroring (bottom-left origin), X-inversion, or X/Y transposition from the correct orientation — it proves only offset. An inverted chart is the worst possible tracker defect (a user marks wrong stitches for hundreds of hours). Violated: the gate's own purpose ("proves the source origin"). Closure: strengthen the fixture specification — (a) non-square grid (width ≠ height); (b) four corner stitches with four *distinct* palette/symbol pairs; (c) at least one asymmetrically placed interior stitch; (d) the compatibility matrix records the full convention (origin corner, X/Y direction, index base, producer+version), not merely an offset.

**R-3 [High, pre-code — blocks persistence] Event-log write contract is incomplete: `localSequence`, multi-tab, idempotency-record content.** The `progressEvents` store is keyed `[projectId, localSequence]` (TD §9.1) but `localSequence` appears nowhere in the `ProgressEvent` contract (§5.2) and its allocation is unspecified; §9.3 derives mark/unmark "from the current committed projection" without stating whether derivation happens inside the same read-write transaction; concurrent tabs of one origin (a real browser scenario) have no single-writer policy — TM-008 covers partial import, not multi-tab. The claimed corruption detection ("reusing an event ID with a different payload is a corruption error") is unimplementable unless `progressEventIds` stores a payload hash. Closure: revised design specifying (a) in-transaction `localSequence` allocation, (b) a second-tab policy (Web Locks single-writer, detection-and-read-only, or equivalent), (c) derivation inside the committing transaction or an explicit staleness rule, (d) `progressEventIds` record content including payload hash; plus a two-concurrent-contexts test added to §11.2.

**R-4 [Medium, pre-code — blocks import-flow persistence] SourceFile blob lifecycle for failed imports is undefined.** TD §9.2 writes the Blob (≤64 MiB) in the first transaction before validation, but for `rejected`/`interrupted` outcomes nothing states whether the blob is deleted; repeated failed imports accumulate orphaned blobs and provoke the very QuotaExceeded failures the design promises to surface. The byte-limit-before-blob-write ordering (§6.1 vs §9.2) is also ambiguous. Closure: explicit retention/deletion rule for failed-import blobs (bounded report retained), explicit statement that byte-limit checks precede blob persistence, and an orphan-absence test.

**R-5 [Medium, pre-code — blocks renderer/apps-web] Missing functional readability and state-visual contracts.** FR-03 ("symbols readable") and the mark-obviousness requirement are currently untestable: (a) no glyph-versus-background contrast policy (a dark glyph on a dark `displayColor` cell is unreadable — the design must require automatic light/dark glyph selection by background luminance, or an equivalent policy); (b) no minimum readable cell size and no defined behavior below that zoom threshold; (c) no visual semantics for `marked` — how a marked cross differs from unmarked and from empty cloth, distinguishable **not only by hue**, across the four states unmarked/marked/saving/not-saved (the optimistic overlay mechanism itself is sound); (d) user-facing coordinate display (including the accessibility status region, TD §8.4) must be **1-based** per counted-chart practice while canonical coordinates remain 0-based internal — one sentence in the contract. Closure: functional rules added to the renderer/client contract (no concrete visual design required — requirements-level rules sufficient for testability).

**R-6 [Medium, pre-code — blocks importer] Symbol identity and glyph-collision rule undefined.** Real OXS files can carry the same `@symbol` code on two different palette items. The design does not define the SymbolDefinition identity key (palette index? source code?) nor what happens on glyph collision across distinct PaletteItems — for the stitcher such a chart is unreadable (legend shows two rows with one glyph). Closure: define the deterministic identity key; on collision emit a stable warning code and apply a documented deterministic disambiguation (e.g., generated fallback for subsequent conflicting items) or an explicitly documented preserve-and-warn decision.

**R-7 [Medium, pre-code — blocks test-suite completeness] Empty/degenerate fixture missing.** Task Package §17 explicitly requires the empty (0-stitch) chart edge case: importer must complete cleanly with a clear message, not crash or reject. TD §11.1's fixture set lacks it. Closure: add the fixture with expected ImportReport and viewer behavior.

**R-8 [High, pre-deploy — blocks production deployment, not coding] HTTP security headers are absent from the delivery design.** Neither TD §12 nor ADR-TS001-004 designs response headers (CSP with `script-src 'self'` and restrictive `connect-src`, `X-Content-Type-Options: nosniff`, `frame-ancestors`/anti-clickjacking, `Referrer-Policy`), and TM-017 defers CSP without owner or deadline while smoke checks (§12.4) never verify headers. CSP is the only *enforceable* backstop for "no embedded content execution" and "no pattern-data egress" when a library defect occurs — TM-004/TM-017 themselves name that residual risk. Closure: a headers section in the delivery design (served by the Worker), header assertions added to pre-promotion and production smoke checks, and a corresponding threat-model entry.

## 4. Non-Blocking Findings (should-fix, with owners)

N-1: no quantified peak-memory budget for the import worker (64 MiB UTF-8 ≥128 MiB as UTF-16 plus object overhead at 500k stitches); add a provisional budget to the Benchmark Plan and link limit tables to expected worst-case peak. N-2: parser behavior when Web Worker creation fails is undefined — either a typed rejection code or a designed fallback; silent main-thread parsing would violate the isolation requirement. N-3: IndexedDB `durability: "strict"` for progress/import commits, or a documented accepted residual in TM-007 (Chromium relaxed durability means "committed" ≠ flushed). N-4: Benchmark Plan — pre-declare the reference device class rather than defining it by the first accepted run; add a reload-with-history metric (projection rebuild/verify at ~10k events); strengthen p95 sampling (≥50–100 iterations or confidence intervals) for gate metrics. N-5: add TM-018 for third-party sample auditability (the only Technical Review §11 item without a TM entry; the §11.1 fixture policy already supplies the control). N-6: declare `Grid` authoritative for width/height and metadata derived (duplication risk). N-7: specify a tap-versus-pan discrimination requirement for touch (false marks are expensive with no undo). N-8 (product disposition, supplied here by Cowork product authority): the bold every-10th grid line is **not required for the Phase 0 slice** — it belongs to Phase 1 viewer aids (rulers/marking) per the approved scope; record in the Phase 1 backlog. N-9 (governance): ADR-TS001-004 and the TD list AU-AGENT-001 as both Owner and Technical Approver; this Bridge review supplies the independent architecture review for TD-GATE-004, and AU-AGENT-003's security review (already named in the Threat Model header) must additionally cover the security-relevant ADR sections before `[PROPOSED]` is lifted — record the independent-review references in the ADR Review History rather than self-approval alone.
