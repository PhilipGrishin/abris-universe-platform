## 1. Task ID
**TASK-THINSLICE-001**

## 2. Название
Тонкий вертикальный e2e-срез Phase 0: канонический Pattern (минимум) + импорт одного простого структурированного формата + Viewer (символы, zoom/pan, тайловый рендер) + отметка/снятие одного стежка + автосохранение.

## 3. Версия постановки
1.1 (редакционная ревизия по PROD-DEC-009; v1.0 сохранена отдельно). Изменения ограничены нормализацией SXP→XSP, привязкой OXS 1.0 и ссылкой на правило фикстур.

## 4. Контекст
Abris Universe («Embroidery OS») — экосистема вокруг вышивки; первая стадия — web-first, с первым тонким вертикальным срезом до наращивания полного P0-ядра (см. `04_Codex_Context_Pack.md`, `01_Product_Vision_and_Roadmap.md` Phase 0). Данная задача — первая передача в технический контур Codex. Источники: Master Product Specification v1.0 (§5.1, §5.2, §5.4, §11, §11.1, §12, §13, EP-01/02/04/05), `02_Architecture_and_Stack.md` (принципы, каноническая модель §3, рендеринг §4, ADR-001/002), решения владельца от 2026-07-20 (DEC-001…DEC-004, `05_Decision_Log.md`).

## 5. Проблема
Сейчас нет ни одной строки production-кода и ни одной проверенной технической реализации доменной модели/рендеринга/процесса Codex↔Claude для этого продукта. Без реального сквозного пути (не изолированных прототипов) риск получить архитектурно несовместимые модули (importer, viewer, progress engine), которые придётся переписывать при масштабировании до 500k стежков и до Phase 1 функциональности.

## 6. Цель
Доказать на реальном (не игрушечном) сценарии, что: (а) каноническая модель Pattern корректно отделяет геометрию/символы/палитру/прогресс; (б) выбранный importer корректно маппит один реальный формат в canonical Pattern с сохранением provenance; (в) viewer рендерит схему тайлово, с читаемыми символами и плавным zoom/pan, без блокировки UI; (г) отметка/снятие стежка мгновенна и переживает reload/крэш благодаря автосохранению. Код и модель данных этого среза — основа Phase 1, не одноразовое демо.

## 7. Пользовательская ценность
Пользователь может: импортировать реальную (простую) схему → увидеть её как читаемую символьную схему с возможностью зумить и панорамировать → отметить сделанный стежок → закрыть и снова открыть проект без потери отметки. Это первый работающий срез Северной звезды продукта (Master Spec §1.1) в миниатюре.

## 8. Приоритет
P0. Блокирует Phase 1 и весь последующий Roadmap.

## 9. Scope

- **EP-01 (минимум).** Каноническая модель Pattern: `Metadata` (размер, count, тип ткани — минимальный набор полей), `Grid` (координатная система, размеры), `Symbols` (визуальные обозначения, независимые от цвета), `Palette` (`PaletteItem`: бренд, код, отображаемый цвет), `Stitches` (только **full cross**, geometry + ссылка на Symbol + ссылка на PaletteItem), `Provenance` (SourceFile, ImportJob, версия importer-а). `PatternVersion` — минимальная запись версии (без миграционной логики, только идентификатор + timestamp).
- **EP-02 (один формат).** Один importer для OXS 1.0 — выбранного по PROD-DEC-009 простого структурированного (не PDF, не изображение) формата. Importer формирует `ImportJob`/`ImportReport` с явными предупреждениями и провенансом.
- **EP-04 (минимум).** Viewer: отображение символов (не только цветных клеток) — TR-VIEW-001; zoom/pan — TR-VIEW-003 (без мини-карты, без jump/центрирования); тайловый/чанковый рендер (принцип 4 архитектуры) — обязателен даже на минимальной схеме, чтобы архитектура была доказана, а не отложена.
- **EP-05 (минимум).** Отметка одного стежка тапом/кликом; снятие отметки (простой toggle, без отдельного «erase mode»); автосохранение состояния прогресса; восстановление после перезагрузки/закрытия вкладки без потери последних действий (NFR-004).
- **Read-only легенда** (символ ↔ цвет), без hide/show, без группировки по типу стежка (Should, не Must, но входит если не создаёт риска для сроков).

## 10. Out of Scope (жёстко)

Прямо и явно **не входит** в эту задачу, независимо от кажущегося удобства реализации:

- Highlight Engine (EP-07) — никакой подсветки символа/цвета.
- Anchors (EP-08).
- Parking (EP-10/11) в любом виде.
- Color Flow (EP-09), сортировки палитры.
- Complexity/heatmap (EP-16).
- Statistics (EP-12), Journal (EP-13), Action Plan (EP-14).
- Undo/Redo в любом объёме (даже 1 шаг) — только простой toggle mark/unmark.
- Bulk-операции («отметить всё видимое», drag/brush-выделение области).
- Fractional stitches, backstitch, French knots, beads, blends, strand count — только full cross в этом срезе (полная модель типов стежков — Phase 1, EP-06).
- Continuous multi-page canvas, мини-карта, линейка, темы, слои, повороты/зеркалирование (TR-VIEW-002/004/005/006/007/008 — Phase 1).
- PDF-импорт (EP-03) и импорт изображений (JPG/PNG) в любом виде.
- Cloud Sync (EP-15), любая серверная синхронизация между устройствами/сессиями — эта задача чисто локальная (один браузер/устройство).
- Inventory/Materials (EP-17).
- Любая community/creator/marketplace/education функциональность (EP-18…EP-23).
- Импорт/экспорт прогресса как отдельная фича, ручной backup.

**Если реализация подсказывает, что «раз всё равно открыт viewer, легко добавить highlight» — это запрещено без отдельного Task Package и решения владельца.** Нарушение Out of Scope рассматривается как отклонение от постановки и должно быть отражено в Completion Report как «не реализовано / расширение scope», а не тихо включено.

## 11. User Flow

**UF-01 (импорт проекта, минимальная версия).** Источник: Master Spec §6. Шаги в рамках среза: (1) пользователь выбирает файл выбранного простого формата; (2) система запускает importer; (3) система показывает результат распознавания и предупреждения (ImportReport), включая явную ошибку для неподдерживаемого/повреждённого файла; (4) пользователь видит базовую сводку (размеры, число цветов/символов); (5) система сохраняет как Project и открывает Viewer. QR-сканирование, выбор формата вручную из нескольких (только один формат поддержан) — вне scope.

**UF-02 (базовая сессия вышивки, минимальная версия).** Источник: Master Spec §6. Шаги: (1) открыть проект (в рамках этого среза — только что импортированный, «последний проект» между сессиями допустим как Should); (2) viewer показывает схему; (3) пользователь может zoom/pan; (4) пользователь тапает/кликает по стежку — отметка переключается (mark/unmark toggle); (5) автосохранение происходит без явного действия пользователя; (6) после reload/закрытия — состояние отметок сохранено. Возврат к последнему viewport, выбор символа/цвета, подсветка, обновление статистики — вне scope (эти шаги UF-02 из Master Spec относятся к Phase 1).

## 12. Функциональные требования

- **FR-01.** Importer детерминированно преобразует файл выбранного формата в canonical Pattern: координаты сетки, символы, палитра (цвет+код бренда), стежки (full cross) должны совпадать с исходной схемой на тестовом эталоне (критерий приёмки MVP, Master Spec §13, адаптировано к объёму среза).
- **FR-02.** При неподдерживаемом/повреждённом файле — понятный, не техническим языком описанный отчёт об ошибке, без падения приложения.
- **FR-03.** Viewer отображает Pattern символами (не цветными клетками) — TR-VIEW-001, читаемыми на используемых уровнях zoom.
- **FR-04.** Zoom/pan — плавные, не блокируют UI, работают на тайловом/чанковом рендере (не полная перерисовка всей схемы на каждый кадр).
- **FR-05.** Клик/тап по клетке со стежком переключает состояние mark/unmark для этой координаты.
- **FR-06.** Изменение прогресса сохраняется автоматически (без явной команды «сохранить») в локальное хранилище.
- **FR-07.** При повторном открытии проекта (после reload вкладки или перезапуска приложения) все ранее отмеченные стежки отображаются как отмеченные.
- **FR-08.** Read-only легенда показывает соответствие символ↔цвет для используемых в схеме элементов палитры (Should).

## 13. Бизнес-правила
Единственное действующее бизнес-правило в этом срезе: одна схема (Pattern/PatternVersion) может иметь ровно один Project в рамках этого среза (многопроектность на одну схему — Phase 1, но модель данных не должна этому препятствовать структурно, см. раздел 18).

## 14. Предметные правила

- **Символ ≠ цвет.** `Symbol` и `PaletteItem` — разные сущности, связанные через `Stitch` (принцип §3.1 архитектуры), даже если в этом минимальном срезе связь 1:1 для full cross — модель обязана допускать будущее many-to-many, не хардкодить association «один символ = один цвет».
- **Схема ≠ прогресс.** `Pattern`/`PatternVersion` неизменны при отметке прогресса; `ProgressEvent`/`Project` — отдельная сущность, ссылающаяся на `PatternVersion`, не встроенная в неё (архитектурный принцип 1).
- **Символы, а не клетки, — единица рендера и легенды.** Viewer и легенда оперируют символами как визуальными единицами (глифами), не «покрашенными клетками»; это ограничивает реализацию (см. раздел 19).

## 15. Состояния
Project: `importing` → `import_failed` (терминальное для этой попытки, с возможностью повторной попытки) | `ready`. Stitch (в рамках Project): `unmarked` | `marked`. Автосохранение: `saved` | `saving` (кратковременное, не блокирующее) — статус `conflict`/`syncing` из архитектуры §5.3 не применим (sync вне scope среза).

## 16. Ошибки
- Неподдерживаемый формат файла → явное сообщение с указанием, какой формат ожидается.
- Повреждённый/частично читаемый файл → ImportReport с перечнем проблем, без падения приложения; частичный импорт не выдаётся за полный (если importer не может гарантировать корректность — явный отказ, не «похожий» результат).
- Ошибка автосохранения (например, переполнение локального хранилища) → пользователь видит статус «не сохранено», не теряет текущую сессию молча.

## 17. Edge Cases
- Пустая/вырожденная схема (0 стежков) — importer должен корректно завершиться с понятным сообщением, а не упасть.
- Схема на грани нижней границы тестового эталона (малый размер) и представитель более крупной схемы (для ранней проверки тайлового рендера, Prototype 9.1) — оба должны быть в наборе fixtures.
- Повторный импорт того же файла — не обязан быть идемпотентным в этом срезе (это Phase 1/EP-01 полная модель, требование «повторный импорт создаёт новую PatternVersion» — зафиксировать как известное ограничение в Completion Report, не блокирует Phase 0).
- Быстрые повторные клики по одному стежку (двойной toggle) — должны давать предсказуемый детерминированный результат (не race condition в локальном состоянии).

## 18. Модель данных (уровень требований, минимальный набор для среза)

| Сущность | Обязательные поля в этом срезе | Примечание |
|---|---|---|
| `Pattern` | id, metadata (name, width, height, count/ткань — минимально), createdAt, provenance-ссылка | Без layers (только full cross), без multi-page |
| `PatternVersion` | id, patternId, formatVersion, createdAt | Без миграционной логики; поле обязано существовать для совместимости с Phase 1 |
| `SourceFile` | id, filename, format, storedRef | Хранение оригинала — обязательно (provenance, принцип 6) |
| `ImportJob` | id, sourceFileId, importerVersion, status, warnings[] | ImportReport — производится из этого объекта |
| `Grid` | width, height, coordinate system | Одна страница/зона, без continuous multi-page |
| `Symbol` | id, glyph/visual reference | Независим от PaletteItem |
| `PaletteItem` | id, brandCode, displayColor | DMC как базовый стандарт (Master Spec §5.3), но в срезе достаточно того, что реально есть в выбранном формате |

## 19. Архитектурные ограничения

- Тайловый/чанковый рендер обязателен (принцип 4) — не «сделаем позже, когда появится 500k», а с первого коммита viewer-а: минимальная тестовая схема должна рендериться через тот же механизм, что и стресс-схема, иначе Prototype 9.1 нельзя будет провести на этом коде.
- Idempotent event log для прогресса обязателен с первого дня (принцип 3), даже при отсутствии sync — чтобы не переписывать модель при появлении EP-15 (Phase 1.5).
- Canonical формат независим от importer-а (принцип 2, ADR-001): importer только маппит внешний формат в canonical Pattern; viewer и progress engine не должны знать, из какого формата пришла схема.
- Provenance обязателен на уровне SourceFile/ImportJob (принцип 6).
- Единый доменный контракт (принцип 7): модель Pattern/Project/ProgressEvent проектируется framework-agnostic (см. рекомендацию `@abris/domain-core` в `02_Architecture_and_Stack.md` §6) — не встраивается напрямую в UI-слой, чтобы не создавать барьер для Phase 2 (mobile).
- Тотальное комментирование (принцип 8, DEC-003): файловый комментарий на каждый доменный модуль, TSDoc публичных интерфейсов domain-core, README на importer.
- Финальный выбор конкретных технологий (рендер-backend, БД, монорепо-инструмент) — предмет Technical Design Proposal Codex; рекомендация — `02_Architecture_and_Stack.md` §6, не обязательство.

## 20. Требования к API и интеграциям
Не применимо в полном объёме — срез не подразумевает внешний API/бэкенд как обязательный компонент (локальное клиентское приложение с локальным хранилищем допустимо для Phase 0, см. `02_Architecture_and_Stack.md` §2 — «ядро первого web-среза»). Если Codex в Technical Design Proposal сочтёт минимальный backend необходимым уже сейчас (например, для единообразия с Phase 1) — это Technical Alternative Proposal, не решается самостоятельно.

## 21. Требования к offline и sync
Проект должен работать полностью локально без сети (принцип offline-first частично уже применим: локальное хранилище, автосохранение). Полная sync-логика (EP-15) — вне scope. Однако структура `ProgressEvent` обязана быть спроектирована так, чтобы EP-15 не потребовал ломающей миграции (idempotent id, timestamp, deviceId — уже в модели раздела 18).

## 22. Требования к безопасности
Базовые: локальное хранилище не должно быть тривиально доступно другим origin (стандартные same-origin гарантии браузера); загружаемый файл схемы обрабатывается без выполнения произвольного кода из содержимого файла (защита от вредоносного контента в импортируемом файле — базовая валидация формата перед парсингом). Полная модель безопасности аккаунтов/платежей — вне scope (нет аккаунтов в этом срезе).

## 23. Требования к privacy
Минимальны в этом срезе: локальный проект не передаётся на сервер, нет персональных данных сверх локально сохранённого файла схемы и прогресса. Не применимо: возрастные ограничения, согласия (нет аккаунтов, нет community).

## 24. Требования к производительности
На основе NFR-001/NFR-002, адаптированных к объёму среза (полная стресс-проверка 500k — Prototype 9.1, отдельно от этой задачи, но инфраструктура рендера должна быть той же):

- Открытие минимальной тестовой схемы — без видимой блокировки UI.
- Zoom/pan — субъективно плавные (целевой FPS и конкретные пороги — устанавливаются и фиксируются Codex на основе раннего прогона Prototype 9.1, не декларируются произвольно здесь).
- Mark/unmark стежка — воспринимается мгновенным (NFR-002), тяжёлые операции (парсинг файла, инициализация тайлов) — вне основного потока UI (Web Worker/эквивалент).
- Автосохранение не должно вызывать заметных задержек/фризов при взаимодействии.

## 25. Требования к аналитике
Минимальны для среза: событие успешного/неуспешного импорта и событие первой отметки стежка достаточно зафиксировать как заготовку под будущий Event Taxonomy (не формализованный документ в этом срезе — см. `06_Documentation_Structure.md` §5). Не блокирует Definition of Done.

## 26. Acceptance Criteria (проверяемые, на основе Definition of Done Phase 0)

1. Импорт реального тестового файла выбранного формата → схема с корректными символами, сеткой, палитрой, совпадающими с эталоном (fixture).
2. Импорт заведомо неподдерживаемого/повреждённого файла → понятная ошибка, без падения приложения.
3. Viewer открывает импортированную схему без блокировки UI.
4. Zoom и pan работают плавно на тайловом рендере (не полная перерисовка схемы как единого объекта).
5. Клик/тап по стежку мгновенно переключает состояние mark/unmark в UI.
6. Состояние отметок сохраняется автоматически без явного действия пользователя.
7. После перезагрузки страницы/повторного открытия — все отметки на месте (ни одна не потеряна).
8. Код и модель данных пригодны как основа Phase 1 (не одноразовый прототип): архитектурные принципы раздела 19 подтверждены НЕЗАВИСИМОЙ архитектурной приёмкой System Architecture Lead (Claude Cowork) на основе кода и Completion Report — self-review Codex не заменяет этот критерий.
9. Ни один элемент раздела 10 (Out of Scope) не реализован даже частично.

## 27. Обязательные тесты

- **Importer:** golden-fixture тест (эталонный Pattern для минимум одного репрезентативного файла выбранного формата) + минимум один негативный тест (повреждённый/неподдерживаемый файл).
- **Progress:** тест persistence (mark → reload → отметка сохранена); тест идемпотентности применения ProgressEvent (повторная доставка одного и того же события по id не создаёт дублирующего эффекта); undo в этом срезе не входит, поэтому undo-тесты не требуются, но это ограничение должно быть явно отмечено в Completion Report как «не тестировалось, т.к. вне scope», не как пропуск.
- **Viewer:** измерение time-to-interactive и FPS при zoom/pan на минимальной тестовой схеме и на второй, более крупной схеме (для ранней сигнализации о Prototype 9.1), плюс измерение mark-latency.
- **Sync:** не применимо к этому срезу (нет сети); тест идемпотентности ProgressEvent (см. выше) — это её функциональный эквивалент на уровне локального event log.

Тестовые эталоны минимум: (а) маленькая схема только с full cross стежками в выбранном формате; (б) схема среднего размера для раннего сигнала о рендер-производительности; (в) минимум один повреждённый/некорректный файл. Создание, хранение и производные этих fixtures подчиняются правилу PROD-DEC-009(3).

## 28. Зависимости

- **DEP-001 (блокирующая).** Выбор конкретного простого формата импорта (spike EP-02/9.5) — должен завершиться до начала кодирования importer-а. Ответственный — System Architecture Lead + Codex.
- **DEP-002 (не блокирующая для старта, но должна быть решена до расширения тайлового рендера в стресс-режим).** Ранний прогон Prototype 9.1 на второй (более крупной) тестовой схеме.
- **DEP-003.** Подтверждение владельцем критерия выбора формата (см. Open Question ниже) — формально не блокирует старт (рекомендация архитектуры уже дана), но должно быть зафиксировано в Decision Log до завершения задачи.

## 29. Риски

- **Преждевременное расширение scope** («раз открыт viewer — легко добавить highlight») — митигируется жёстким Out of Scope (раздел 10) и обязательным Technical Review перед стартом.
- **Выбор формата окажется нерепрезентативным** для будущих реальных форматов (EP-02 полного состава) — митигируется тем, что spike сравнивает 2–3 кандидата, а не берёт первый попавшийся.
- **Тайловый рендер спроектирован «условно», без реальной проверки на что-то крупнее минимальной схемы** — митигируется требованием раздела 24/27 включить вторую, более крупную тестовую схему уже в этом срезе.
- **Архитектурный долг под видом «временного решения для MVP»** — запрещено декларировать «временное» без явной пометки в Completion Report как known issue/technical debt с точной формулировкой, что именно нужно будет переделать в Phase 1.

## 36. Требования к rollback
Поскольку это первая реализация (нет предыдущей production-версии для отката), rollback-требование — способность откатить сам деплой/сборку до пустого состояния без повреждения структуры репозитория; явных пользовательских данных для миграции назад нет. Codex обязан описать, как откатить именно эту поставку (например, через feature flag или отдельную ветку/тег), если что-то в Independent Acceptance окажется блокирующим дефектом.

## 38. Обязательная инструкция Codex (независимый Technical Review)

До начала реализации проведи независимый технический review постановки и существующего репозитория.

Не принимай требования автоматически.

Проверь:
— реализуемость;
— архитектуру;
— текущий код;
— зависимости;
— миграции;
— безопасность;
— производительность;
— тестируемость;
— совместимость;
— риск регрессии;
— rollback.

Если постановка содержит противоречие, скрытую зависимость, опасное решение или требует изменения продуктовой логики, не изменяй её самостоятельно.

Подготовь Clarification Report, Conflict Report или Technical Alternative Proposal и верни его в Claude Cowork до реализации соответствующей части.

Это в равной мере касается открытого вопроса OQ-005 (выбор формата импорта) — Codex обязан провести технический spike и представить обоснование выбора как часть Technical Review, а не как самостоятельное продуктовое решение, принятое без фиксации в Decision Log.
