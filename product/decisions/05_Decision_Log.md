## Часть A. Конфликты Master Spec (C-01…C-10)

Источник контекста и вариантов — Master Spec §19; статус и рекомендация — синтез Master Spec + `01_Product_Vision_and_Roadmap.md`.

### C-01 — PDF в MVP
- **Дата регистрации:** Master Spec v1.0 (июль 2026); пересмотрено в Roadmap 2026-07-20.
- **Контекст:** Один блок исходников определяет PDF-конвертер обязательным для MVP, другой — прямо исключает полноценное сканирование/конвертацию PDF из первого MVP.
- **Варианты:** (а) полный PDF-конвейер в MVP; (б) исключить PDF из MVP полностью; (в) разделить machine-readable и scanned/photo PDF, поддержать первую группу раньше.
- **Статус:** **Recommended-pending-owner.** Разделение (в) принято как рабочая рекомендация команды и отражено в Roadmap (EP-03 → Phase 1.5, machine-readable; scan/photo — позже). Конкретный SLA распознавания (confidence %, доля успешного импорта) **не решён** — см. OQ-006.
- **Рекомендация команды:** Провести технический spike (Prototype 9.2, 20–30 реальных PDF) до фиксации SLA; в Phase 0/1 PDF не входит вообще.
- **Кто принимает решение:** владелец проекта — по итогам spike 9.2 (SLA и объём Phase 1.5).
- **Затронутые эпики/фаза:** EP-03, Phase 1.5.

### C-02 — JPG/PNG (растровые изображения / фото схем)
- **Контекст:** В одном PRD распознавание изображений обязательно, в оценочном scope — опционально.
- **Варианты:** (а) полноценное распознавание символов/цвета по фото в MVP; (б) полностью исключить; (в) отложить автоматическое распознавание, разрешить «image-as-background + ручная разметка» как отдельный режим (сближение с Markup-подходом).
- **Статус:** **Resolved-derived.** Вариант (в) закрыт как рабочая рекомендация — отложено, распознавание не считается «простым импортом» (Master Spec §5.1).
- **Кто принимает решение:** уже закрыто рекомендацией; переоткрывается только при явном Change Request.
- **Затронутые эпики/фаза:** EP-02 (частично), Phase 2+ (при пересмотре).

### C-03 — Community в MVP
- **Контекст:** Lean Canvas/Mind Map включают community уже в MVP; оценочное ТЗ исключает социальную сеть из MVP.
- **Варианты:** (а) полноценная соцсеть в MVP; (б) полностью исключить любую community-модель данных из MVP; (в) исключить ленту/группы/челленджи из MVP, но заложить profile-ready архитектуру и share-карточки.
- **Статус:** **Resolved-derived.** Вариант (в): полноценный Community Layer — Phase 3b (EP-18); доменная модель Phase 1 обязана быть совместимой (не блокировать) с последующим появлением профиля/ленты.
- **Кто принимает решение:** закрыто; System Architecture Lead контролирует, что модель User/Project остаётся profile-ready.
- **Затронутые эпики/фаза:** EP-18, Phase 3b.

### C-04 — Cloud sync
- **Контекст:** Экосистемная ценность продукта требует cloud sync; оценочное MVP-scope допускает работу без sync.
- **Варианты:** (а) sync обязателен с Phase 1; (б) sync не нужен вообще для web; (в) sync — отдельный P1-эпик, не откладываемый после появления нескольких платформ.
- **Статус:** **Recommended-pending-owner.** Вариант (в) принят как направление: локальный MVP возможен для одной платформы (Phase 0/1 — только web, sync не входит); при появлении Mobile (Phase 2) sync становится обязательным. **Открыт** конкретный момент проактивного введения — Roadmap рекомендует ввести Cloud Sync уже в Phase 1.5 (де-риск перед Phase 2), но это не решение владельца — см. OQ-007.
- **Рекомендация команды:** ввести Cloud Sync (offline-first база) в Phase 1.5, а не откладывать до Phase 2.
- **Кто принимает решение:** владелец проекта.
- **Затронутые эпики/фаза:** EP-15, Phase 1.5 (рекомендация) / Phase 2 (обязательно).

### C-05 — Parking priority
- **Контекст:** В одном PRD парковка — must-have MVP; в детализации функций — отнесена к MVP+/MVP2.
- **Варианты:** (а) полный Parking Styles Engine в MVP; (б) исключить парковку из MVP; (в) simplified deterministic parking (classic/block) — Must для MVP, full engine (diagonal/snake/waterfall/AI) — P1.
- **Статус:** **Resolved-derived.** Вариант (в) закрыт: Simplified Parking (EP-10) — Must в Phase 1 (повышено до критерия приёмки MVP в Roadmap); Advanced Parking Engine (EP-11) — Phase 1.5.
- **Кто принимает решение:** закрыто.
- **Затронутые эпики/фаза:** EP-10 (Phase 1), EP-11 (Phase 1.5).

### C-06 — Smart Complexity
- **Контекст:** Уникальная дифференцирующая функция, но исходники относят её к высокой сложности и MVP2.
- **Варианты:** (а) полная AI-модель сложности в MVP; (б) исключить полностью; (в) lite детерминированная heatmap как отдельный P1-эпик, персонализированная AI-модель — позже.
- **Статус:** **Resolved-derived.** Вариант (в): EP-16 lite — Phase 1.5, детерминированно, без AI; веса/пороги формулы сложности остаются `[OPEN]` внутри самого EP-16 (методика и пользовательское тестирование — предмет отдельного research-задания, не блокирует Phase 0/1).
- **Кто принимает решение:** Research & Product Analytics Lead — по методике; владелец — по срокам P1/P2 полной модели.
- **Затронутые эпики/фаза:** EP-16, Phase 1.5/2.

### C-07 — Создание схем (Creator Hub)
- **Контекст:** Общая экосистемная концепция включает создание схем; стартовый продукт (viewer+tracker) их исключает.
- **Варианты:** (а) Creator Hub параллельно с tracker с самого начала; (б) исключить навсегда; (в) Creator Hub только после стабильного tracker-ядра.
- **Статус:** **Resolved-derived (условиями и порядком).** Вариант (в): EP-19 — Phase 3a, условие входа — стабильное ядро (Phase 0–1.5 завершены и прошли Verified).

- **Затронутые эпики/фаза:** EP-19, Phase 3a.

### C-08 — Поддержка бисера
- **Контекст:** Общая продуктовая идея декларирует поддержку бисера; функциональные описания tracker-а сфокусированы в основном на cross-stitch.
- **Варианты:** (а) полная поддержка бисера с MVP наравне с крестом; (б) исключить бисер полностью из ранних фаз; (в) определить модель данных для бисера и тестовые fixtures до обещания полной поддержки.
- **Статус:** **Open.** Ни один вариант не закрыт официально; рекомендация — (в). В доменной модели `Layers`/`StitchType` бисер архитектурно предусмотрен как расширяемый тип (не блокируется), но объём функциональной поддержки в Phase 1 не определён.
- **Кто принимает решение:** Embroidery Domain & UX Lead (модель) + владелец (объём для Phase 1).
- **Затронутые эпики/фаза:** EP-06, Phase 1.

### C-09 — Marketplace scope
- **Контекст:** Экосистема предполагает схемы, наборы, готовые работы, услуги и курсы одновременно; ресурсно это широкий фронт.

- **Кто принимает решение:** закрыто; порядок последующих категорий — Ecosystem, Community & Commercial Product Lead.
- **Затронутые эпики/фаза:** EP-20, EP-21, Phase 3c.

### C-10 — Онлайн-выставки
- **Контекст:** Идея присутствует в исходниках как дискуссионная; не решено, делать ли вообще и относится ли это к Community или Marketplace.

## Часть B. Решения владельца от 2026-07-20

### DEC-001 — Платформенная последовательность: web-first, mobile отдельно
- **Дата:** 2026-07-20. **Тема:** Порядок реализации платформ.
- **Контекст:** NFR-003 требует Android/iOS/Web с единой функциональной моделью, но не задаёт порядок.
- **Варианты:** (а) параллельная разработка всех платформ; (б) mobile-first; (в) web как полигон, отдельное мобильное приложение позже на общем доменном ядре.
- **Выбранный вариант:** (в).
- **Обоснование:** минимизация операционного риска, более быстрая обкатка доменной модели, архитектуры рендеринга и Codex-процесса на одной платформе перед тиражированием.
- **Последствия:** Roadmap перестроен на Phase 0→1→1.5 (web) → Phase 2 (mobile) → Phase 3 (экосистема); NFR-003 уточнён в части порядка, не паритета.
- **Статус:** **Resolved.**
- **Условия пересмотра:** Change Request владельца.
- **Автор решения:** Project Owner. **Утверждающий:** тот же.
- **Затронутые модули:** весь продукт. **Связанные документы:** `01_Product_Vision_and_Roadmap.md` §2, §Phase 2.

### DEC-002 — Scope первого тонкого вертикального среза (Phase 0)
- **Дата:** 2026-07-20.
- **Контекст:** Нужен минимальный, но настоящий e2e-срез для обкатки ядра до наращивания полного P0.
- **Варианты:** (а) сразу полный Phase 1/MVP; (б) изолированные прототипы без сквозного пути; (в) один сквозной тонкий срез: canonical Pattern (мин.) + импорт одного простого формата + viewer символы/zoom-pan + отметка стежка + автосохранение.
- **Выбранный вариант:** (в).
- **Обоснование:** доказывает жизнеспособность доменной модели и рендер-архитектуры на реальном пути раньше, чем расширяться вширь; снижает риск тупиковой модели.
- **Последствия:** жёсткий Out of Scope (без highlight/anchors/parking/статистики/undo-redo/bulk/PDF/cloud) для Phase 0 — см. `07_TaskPackage_EP01_ThinSlice.md`.
- **Статус:** **Resolved.**
- **Условия пересмотра:** только по итогам Definition of Done Phase 0 (переход к Phase 1) или Change Request.
- **Связанные документы:** `01_Product_Vision_and_Roadmap.md` Phase 0; `07_TaskPackage_EP01_ThinSlice.md`.
